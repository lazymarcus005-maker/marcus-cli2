# T-022 — Recovery, Migration and Interruption Hardening Matrix

**Phase:** 7 — Release Hardening
**Depends on:** T-004, T-005, T-018, T-019, T-021
**Sources:** spec.md sections 32, 38, 45–46; handoff.md sections 9, 13, 15

## Goal
Prove that Macus resumes safely across crash/interruption boundaries without duplicate unknown side effects or source rollback.

## Scope
Expand recovery tests and reconciliation logic for:
- termination before tool launch;
- after launch but before lifecycle acknowledgement;
- after file write but before result persistence;
- after durable result persistence but before transcript completion;
- during model stream;
- during compaction;
- during schema migration;
- external editor changes;
- branch/HEAD changes;
- worktree mismatch;
- concurrent sessions/processes;
- cancellation;
- unavailable/expired logs;
- unknown shell/external effects.

Recovery order must acquire the mutation lock, verify identities/schema, load Pi transcript through supported APIs, load matching state revision, reconcile execution journal with transcript/filesystem evidence, repair/represent incomplete exchanges through supported APIs, revalidate source/index/test evidence and only then permit new mutation/model dispatch.

## Acceptance Criteria
- [ ] No unknown side-effecting execution is automatically replayed.
- [ ] Completed durable result is not appended twice.
- [ ] File writes reconcile with known before/after hashes; unexpected hash becomes conflict.
- [ ] Unsupported transcript repair pauses safely; Pi files are never hand-patched.
- [ ] Schema migrations are transactional and crash-tested.
- [ ] External edits/branch changes invalidate stale source and evidence.
- [ ] Concurrent second mutator remains blocked.
- [ ] Cancellation never silently resumes.
- [ ] Every unsupported recovery state preserves evidence and reports a safe pause.

## Evidence
Maintain a recovery matrix with injected failure point, expected state, observed state, replay decision and evidence/log reference.
