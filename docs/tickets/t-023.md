# T-023 — Performance Harness and Paired Pi vs Macus Benchmark Report

**Phase:** 7 — Release Hardening
**Depends on:** T-008, T-022
**Sources:** spec.md section 39 and section 45; handoff.md section 14

## Goal
Measure performance and quality under controlled paired conditions and publish raw evidence without inferring savings from context size alone.

## Scope
Use the Phase 1 harness and pinned Pi baseline. Build/version the mixed TS/JS/C# reference fixture of 10,000 included source files and about 100 MiB text, or clearly label a non-reference fixture.

Measure:
- warm startup to usable prompt;
- warm bounded text search;
- verified cached symbol read;
- single-file index refresh;
- idle CPU;
- CLI/indexing peak RSS;
- cold indexing duration/RSS/files per second;
- end-to-end coding tasks including discovery, edit/test, large output, ambiguity, compaction and crash/resume.

For task comparisons run at least three paired Pi/Macus repetitions with identical starting revision, prompt, model endpoint/version, generation settings, context/output limits and oracle. Reset workspaces between runs and separate cold/warm repository and provider-cache conditions where known.

Record correctness first, then all input/output tokens including retries/compaction, cached input if reported, wall time, first useful edit, tool calls, peak context and CLI memory.

## Acceptance Criteria
- [ ] Raw per-run data is preserved.
- [ ] At least three paired repetitions exist per reported task/condition.
- [ ] Run order/cache conditions are documented.
- [ ] Quality regression gate reports any newly failing fixed-suite cases.
- [ ] Hardware differing from Mac mini M4 Pro 48 GB is labelled and does not claim the reference gate.
- [ ] Token/latency improvement claims are limited to measured conditions.
- [ ] No cost claim exists without an explicit pricing source/config.
- [ ] Performance targets are reported as pass/fail/pending, never fabricated.

## Deliverable
Publish docs/benchmark-report.md plus machine-readable raw metrics.
