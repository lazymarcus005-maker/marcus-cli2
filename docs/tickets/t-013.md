# T-013 — Request Manifests, Provenance and Context Inspector

**Phase:** 3 — Context Runtime
**Depends on:** T-012
**Sources:** spec.md sections 6.4–6.5, 29; handoff.md sections 5.1–5.2, 11

## Goal
Make every dispatched request auditable: what source was included, what was omitted, why, and how the budget was calculated.

## Scope
Attach provenance to source fragments: fragment ID, source path, optional symbol ID, 1-based range, reason, tier, ranking score, current content hash, index generation, freshness and estimated tokens.

Persist a request manifest for every provider dispatch with request/session/model identifiers, instruction hashes, included fragment IDs/hashes, omissions/reasons, category totals, estimation method and adapter/Pi versions. Do not copy secrets or unnecessary full raw source into manifests.

Expand /context to show the actual last dispatched request and separately labelled prospective next-request estimate. Add /context files for included/omitted fragments, freshness, reason, tier, hash, token estimate, truncation and uncertain relationship evidence.

Use mutually exclusive top-level categories so category totals exactly sum to estimated prompt total.

## Acceptance Criteria
- [ ] Every dispatch has one request manifest.
- [ ] Included fragments are traceable to current source hashes.
- [ ] Omitted fragments carry a concrete reason.
- [ ] Category totals exactly sum without double counting.
- [ ] Provider-reported usage is separately labelled from estimates.
- [ ] Stale/uncertain fragments are visible in inspection output.
- [ ] No credential or secret value is stored/displayed.
- [ ] Manifests reflect the actual payload sent through Pi, not a pre-selection wish list.

## Tests
Compare captured provider payloads to manifests across multiple tool turns, deduplication, omissions, stale fragments, model switches and provider-usage reporting.
