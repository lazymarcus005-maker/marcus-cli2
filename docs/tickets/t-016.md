# T-016 — Test Execution, Structured Evidence and Error-Focused Retrieval

**Phase:** 4 — Coding Workflow & Evidence
**Depends on:** T-005, T-015
**Sources:** spec.md sections 17–18, 36; handoff.md sections 12–13

## Goal
Produce truthful test/build evidence tied to the exact working snapshot and use failures to retrieve only relevant current source.

## Scope
Discover test commands from project configuration/instructions and execute through Policy Executor. Implement structured adapters for Node/JUnit-compatible reports and .NET TRX. Unknown runners remain usable but test counts/status must be unknown when evidence is insufficient.

Persist command, cwd, timing, exit code, signal, timeout/cancel flags, output completeness, parser ID/version/status, test counts, failure excerpts, log reference, repository identity, HEAD, tested snapshot digest and evidence status.

Snapshot digest must include relevant dirty source/config and untracked inputs; HEAD alone is insufficient. Invalidate successful evidence after a relevant edit or conservatively when dependency coverage is unknown.

Parse diagnostics into authorized bounded file/line/symbol retrieval. Normalize paths and revalidate source before reading.

## Acceptance Criteria
- [ ] Zero discovered tests is not passed.
- [ ] Timeout, cancellation, command failure and incomplete parser output cannot become passed.
- [ ] Unsupported/partial parsing produces unknown counts/status.
- [ ] A complete structured report may establish counts even when console output is truncated.
- [ ] Source inputs changing during test execution mark evidence stale/unknown.
- [ ] Later relevant edits invalidate green evidence.
- [ ] Diagnostic paths cannot escape authorized roots.
- [ ] Failure fingerprints include normalized diagnostic/location/source version.

## Tests
Successful/failed structured reports, parser failure, partial report, zero tests, timeout, cancellation, large output, stale evidence and diagnostic-path attack cases.
