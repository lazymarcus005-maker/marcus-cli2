# T-018 — Context Ledger and State Checkpoints

**Phase:** 5 — Durable Context & Optimization
**Depends on:** T-004, T-017
**Sources:** spec.md sections 19–20, 31–32, 38; handoff.md sections 5.5, 9–10

## Goal
Persist bounded durable task context and user-visible checkpoints without creating a second transcript or source rollback mechanism.

## Scope
Implement the optional session-scoped Context Ledger in state.db. Store goal, decisions with provenance, working/changed files and hashes, task references, evidence references, blockers and next action. Each update has a revision and session ID. Derive test status from current evidence.

Implement checkpoints containing schema version, session/repository/worktree identity, Pi transcript entry reference, state revision, goal, task states, decisions, changed paths/hashes, important symbols, evidence/failures, next action and pending/unknown executions.

Write checkpoints via temp file + flush + atomic rename, then register transactionally. Reconcile orphan/incomplete checkpoint records on startup.

## Acceptance Criteria
- [ ] Ledger is bounded and does not duplicate editable Pi transcript history.
- [ ] Old evidence cannot remain green after relevant source changes.
- [ ] Checkpoint restore never rewrites source bytes or performs Git reset/checkout.
- [ ] Restore compares identity and file hashes and invalidates stale evidence/context.
- [ ] Incomplete checkpoint files are never treated as committed.
- [ ] Disabling ledger still preserves core session/journal resume.
- [ ] Disabling checkpoint still preserves core atomic persistence/resume.
- [ ] Reduced recovery metadata is visible when optional features are disabled.

## Tests
Ledger revision atomicity, stale evidence, checkpoint crash during write, orphan reconciliation, worktree mismatch, restore after source edit and supported flag combinations.
