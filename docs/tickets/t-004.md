# T-004 — Durable State, Sessions, Journal and Worktree Lock

**Phase:** 1 — Agent Foundation & Safety
**Depends on:** T-001
**Sources:** spec.md sections 5.3, 19–20, 32, 38; handoff.md sections 5.5–5.6, 9

## Goal
Establish transactional durable state and crash-safe run/session identity before higher-level workflow features.

## Scope
Create .macus/state/state.db with SQLite transactions, foreign keys, schema versioning, WAL and synchronous FULL on supported local filesystems.

Core tables must cover sessions, runs, tasks, ledger_revisions, executions, execution_events, test_evidence, checkpoints and schema_metadata, even where later features are not yet exposed.

Implement canonical repository/worktree identity binding, session isolation, run identity/state revisions, execution journal lifecycle prepared → started → completed/failed/cancelled/unknown, transcript references rather than duplicate editable message history, OS-backed exclusive mutation lock per worktree, read-only inspection from another terminal and versioned transactional migrations.

On startup/resume reconcile journal, Pi transcript references and filesystem state before new mutation. Never automatically replay a side-effecting execution with unknown outcome.

## Acceptance Criteria
- [ ] Two sessions keep state fully isolated.
- [ ] Second mutating process on the same worktree is refused.
- [ ] Stale PID files are not the locking mechanism.
- [ ] Crash after a write but before result persistence does not cause duplicate replay.
- [ ] Moved/mismatched worktree requires explicit rebinding.
- [ ] Corrupt cache can be rebuilt without touching durable state.
- [ ] Unsupported/corrupt durable state is preserved and reported.
- [ ] Pi transcript remains Pi-owned.

## Tests
Session isolation, second-writer rejection, migration rollback, crash boundaries, unknown outcome and worktree mismatch.
