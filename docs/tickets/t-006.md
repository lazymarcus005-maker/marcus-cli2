# T-006 — Effective Request Budget and Protocol Guard

**Phase:** 1 — Agent Foundation & Safety
**Depends on:** T-002, T-003, T-005
**Sources:** spec.md sections 6, 6.4–6.5, 17, 24–25, 29; handoff.md sections 5.1–5.2

## Goal
Prove that Macus controls the actual provider request size and protocol before every dispatch, not merely a UI working-set estimate.

## Scope
Implement the Phase 1 request composer and budget guard around Pi request preparation.

Invariant: estimated_full_request + reserved_output_tokens + safety_margin_tokens must be less than or equal to validated_model_context_window.

Count system/runtime instructions, repository instructions, tool schemas, retained chronological history, tool exchanges, current user input, retrieved/tool content and provider framing estimate.

Use a matching tokenizer where available; otherwise use a clearly labelled conservative estimate. Keep provider-reported usage separate from prospective estimates. Preserve mandatory user constraints, pending tool obligations, unresolved recovery state and valid call/result groups. If mandatory content cannot fit safely, pause before dispatch.

Allow one bounded rebuild/compaction retry after a context-length rejection; never retry the identical oversized request indefinitely.

## Acceptance Criteria
- [ ] Every provider request, including inner tool turns and compaction, passes the guard.
- [ ] Threshold ratios use usable prompt capacity after output/margin reservation.
- [ ] Category caps are aggregate, not per call.
- [ ] Model switch recomputes limits before the next request.
- [ ] Unknown/invalid model limits block dispatch.
- [ ] Tool protocol groups and chronological order remain valid.
- [ ] Basic /context exposes last-request estimate method and separately labelled provider usage.

## Tests
Capture actual dispatched payloads across multiple turns and verify size, framing/tool-schema accounting, invalid budgets, smaller-model switching, mandatory-overflow pause and one-retry behavior.
