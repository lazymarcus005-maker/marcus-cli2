# T-011 — Smart Read, Repository Map and Phase 2 Freshness Gate

**Phase:** 2 — Code Retrieval & Freshness
**Depends on:** T-009, T-010
**Sources:** spec.md sections 9–10, 14, 16, 45; handoff.md sections 6, 8

## Goal
Expose fresh bounded source reads and a compact repository map without treating cached ranges as source truth.

## Scope
Implement read_symbol, read_range and expand_context using current file hashes. Reads return numbered 1-based inclusive ranges, current file hash, signature/body and minimal type/import context where useful.

On stale/deleted/ambiguous symbol, fail clearly or refresh/fall back to a bounded fresh read. Large bodies return truncation and continuation metadata.

Implement a lightweight repo map containing important files, symbols, selected signatures and dependencies, with default 1200-token budget. Reduce map priority once the working set becomes clear. Never inject full implementations.

Create docs/phase-2-evidence.md.

## Acceptance Criteria
- [ ] Cached ranges are revalidated against disk before being returned.
- [ ] Read-before-edit observed hashes are available for the edit safety contract.
- [ ] Ambiguous or deleted symbols are not silently redirected.
- [ ] Repo map remains within configured token budget.
- [ ] External edits, rename/delete and branch checkout cannot leave stale source presented as current.
- [ ] Degraded index still allows ripgrep and bounded range reads.
- [ ] Phase 2 CLI exercise demonstrates search → locate → smart read with a reproducible fixture.
- [ ] Common phase gate tests/typecheck/build/lint and diff review are recorded.

## Evidence
Document language/parser versions, freshness/invalidation cases, exclusions and symlink tests, commands, results and blockers.
